# Disaster recovery

Restoring Vardo onto a new host needs the backup bucket plus two escrowed secrets: the encryption master key and the auth secret. The bucket alone is not enough.

## The encryption master key

`ENCRYPTION_MASTER_KEY` encrypts every app's env vars, every backup target credential, the GitHub App private key, every deployment env snapshot and every backup archive. It is generated by `install.sh` into `/opt/vardo/.env` (root-owned, mode 600).

It is deliberately in no backup. An archive that carried it would hand every secret to whoever holds the archive — the key and the ciphertext would share one blast radius, which is the thing encryption is for.

So it has to be escrowed separately, once, by hand:

```bash
sudo vardo key
```

It prints `ENCRYPTION_MASTER_KEY` and `BETTER_AUTH_SECRET`. Store both in a password manager at install time; neither can be derived later.

`BETTER_AUTH_SECRET` encrypts two-factor secrets. Without it, users with two-factor sign-in can't sign in after a restore until it's reset.

### Key ID

The backups page shows a **Key ID** — a one-way fingerprint of the running key, like `k1:3f2a9c8e14b7d056`. It reveals nothing about the key. Record it alongside the escrowed copy so you can confirm a restored key is the right one before you restore anything.

Vardo records the same fingerprint in its own database, so it travels inside the system backup. On every startup the running key is checked against it:

| State | Meaning |
| --- | --- |
| `ok` | The running key is the one this database's ciphertext was written with. |
| `mismatch` | The database was written with a different key. Every env var in it is unreadable. |
| `unrecorded` | Nothing on file yet — a fresh install, or an instance upgraded from before this check. |
| `unconfigured` | No `ENCRYPTION_MASTER_KEY` is set. |

A mismatch, or any value the running key cannot decrypt, is logged at error level on startup and shown on the backups page.

## Restoring onto a new host

1. Install with the restore flag. It asks for the escrowed secrets and the backup storage, or reads them from `ENCRYPTION_MASTER_KEY`, `BETTER_AUTH_SECRET` and `VARDO_BACKUP_*`:

   ```bash
   sudo ./install.sh --restore
   ```

2. Open the setup page and choose **Restore from backup**. Pick a system backup and enter the master key. Nothing is restored until the backup's Key ID matches the key and its two-factor secrets open with the auth secret.
3. Vardo's database comes back first. Sign in with an account from the backup to follow the apps as they restore and redeploy, in priority order.
4. Backup and cron jobs stay paused. Resume them from the same page once the old host is off, or both write to the same bucket.

If the instance was installed without the escrowed secrets, load them with `sudo vardo key set` and reload the setup page. `vardo restart` doesn't pick up a changed `.env`; `key set` recreates the container so it does.

### If the key is lost

Nothing recovers the env vars. Re-enter them per app; everything else in the backup (apps, projects, domains, volumes, deployment history) restores normally. Deploys refuse until each app's env vars are readable again, which is deliberate — a deploy with a silently empty environment is worse than no deploy.

## Restoring a single app's data

Every archive is encrypted with its own key, wrapped by the master key, so app volume and database archives need the master key too. Restore them from the app's Backups tab; downloads and restore drills decrypt on the server. Archives written before encryption have no header and restore as they are.

Encrypted archives end in `.enc` on the target (`.tar.gz.enc`, `.dump.gz.enc`); archive tools can't open them as they are. Archives written before the suffix keep their plain names but are still encrypted. To open one without Vardo running, copy it off the target and decrypt it on the host:

```bash
sudo vardo backup decrypt 2026-10-06T02-00-00-000Z.tar.gz.enc data.tar.gz
```

The command reads the key from `/opt/vardo/.env`, or from `ENCRYPTION_MASTER_KEY` if set. The archive header carries everything else, so no database is needed. A corrupt, truncated or tampered archive fails instead of writing partial output.

## What a backup does not contain

- The encryption master key. Without it, no archive decrypts.
- Container images — pulled from your registry on deploy.
- `/opt/vardo/.env` itself, including `DB_PASSWORD` and `BETTER_AUTH_SECRET`. Losing the auth secret signs everyone out; losing the master key is the unrecoverable one.
